# bsdfs_lean


# bsdfs Folder

Lean4 code for the `bsdfs` algorithm with proofs of its main properties/theorems:

- soundness: every output is a simple s-t path with at most k edges,
- completeness: every such path is output exactly once,
- worst-case delay: every interval (o_τ, o_{τ+1}] costs at most 2k(n + m) steps,
- amortized delay: the τ-th observable event (start, output, termination)
  happens after at most τ(k+2)(n+m) steps.

All Lean code was generated by Anthropic Claude Opus 5.5 (at Max level) within less than
half a day from the following sources
- preprint https://arxiv.org/abs/2607.14745 containing all lemmas, theorems, and proofs,
- several additional notes, and
- a Python reference implementation (https://github.com/FrankBau/bsdfs).

The Lean Core (https://lean-lang.org/) version 4.34.1 was used (Visual Studio Code plugin) 
for automated proof-checking; no additional libraries. Details are in the Readme.md.


# Python Folder

'bsdfs` reference implementation in Python with a smoke test, demonstrating that the
Lean translation generates the same execution traces as the Python implementation 
in 1000+ instances. Details are in the Readme.md.


# The Current State (by Claude)

- **Verified:** the four theorems `bsdfs_sound`, `bsdfs_complete_once`, `bsdfs_worst_case_delay` and `bsdfs_amortized_delay`. They have no `sorry` and use only the standard axioms. The Lean kernel checks the final proof terms, so `mvcgen` being experimental doesn't affect trust. What you have to read and trust is the ~150 lines of definitions in `BsdfsExec.lean`: `Graph`, `bsdfs`, `outputs`, `obsSteps`, `BoundedPath`, `Graph.m`.
- **Path mode only:** all four theorems assume s ≠ t. Cycle mode (s = t) is in the paper's title and in the smoke test (200 instances), but no theorem covers it yet.
- **The verified object is the Lean transcription:** its agreement with `bsdfs_traced.py`, the paper's pseudocode and the C code is tested on the 1203 smoke instances, not proved.
- **The delay bounds count the step counter:** that is the paper's cost model, with stack membership as an O(1) step. The Lean executable actually checks membership by a linear scan, so the theorems say nothing about the Lean program's own running time.
- **Not formalized:**
  - the lower bounds (gate traps Γ_c, tightness);
  - the refinements in `visits.md` and `edge_budget.tex` (2k−2j−1 per inner interval, the terminal k+2, locality, bounded degree);
  - the paper's lemmas in their original spine/fork wording. The Lean proofs use stack-model versions; they match the paper by construction, but that match isn't proved.

So it's fair to say the four main claims are machine-checked for path mode, on the Lean model of the algorithm.
